# ADR 0003 — интеграция с OpenClaw

**Дата:** 2026-10-23
**Статус:** принято

## Контекст

OpenClaw должен уметь читать состояние семьи, отвечать в Telegram, запускать автоматизации
и предлагать решения. Прямой доступ к Postgres или «универсальный SQL-инструмент» — плохая идея:
риск утечки, обхода RBAC и необратимых ошибок.

## Решение

MCP-сервер с **узкими типизированными инструментами**, стоящий перед API.

```
OpenClaw agent
   │ MCP (stdio/HTTP)
   ▼
packages/openclaw-plugin  ── HTTPS + scoped token ──▶  apps/api
   │                                                    │ RBAC + audit
   └─ schemas, validation, confirm-flow                 ▼
                                                     Postgres
```

Правила:
1. Никакого SQL и произвольных запросов.
2. Каждый инструмент — явная схема (zod), ограниченный набор полей.
3. Scope на токене: `money:read`, `money:write`, `guard:write`, `pantry:read` и т.д.
4. Записывающие операции создают **черновик** или требуют `confirm_token`.
5. Аудит каждого вызова в `agent_audit` (кто, что, результат, длительность).
6. Агент не может менять свои scope, отключать аудит или удалять историю.

## Формат ответов

Все инструменты возвращают:

```json
{
  "ok": true,
  "data": { },
  "meta": { "asOf": "2026-10-23T10:00:00Z", "currency": "PLN" }
}
```

Ошибки — `{ "ok": false, "error": { "code": "FORBIDDEN", "message": "..." } }`.
Агент обязан показывать человеку `asOf`, если данные не в реальном времени.

## Почему не плагин внутри OpenClaw

MCP-сервер переиспользуем: тот же код могут вызывать другие агенты и локальные скрипты.
Плагин OpenClaw остаётся тонким — скиллы и подсказки, без бизнес-логики.

## Последствия

- Нужно поддерживать две поверхности: MCP-схемы и REST.
- Ошибки в схемах видны сразу (тесты контрактов).
- Автоматизации («каждый вечер дайджест») живут в OpenClaw, а не в API: проще менять.
