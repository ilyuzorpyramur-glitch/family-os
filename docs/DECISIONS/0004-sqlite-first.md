# ADR 0004 — SQLite-first и прямой API Zen Money

**Дата:** 2026-10-23
**Статус:** принято для M1

## Контекст

Приложение должно ставиться «как Grocy»: один контейнер, один том, без внешней БД.
Семья — это 2–5 человек и десятки тысяч операций, а не SaaS с тысячами тенантов.
При этом в ADR 0001 предполагались Postgres и Prisma, а в ADR 0002 — банковский
агрегатор GoCardless.

Пользователь уточнил: деньги берём из Дзен-мани по токену, сервер — самостоятельный.

## Решение

1. **Хранилище:** SQLite (WAL) + `better-sqlite3`, схема в `apps/api/src/db.ts`,
   миграции — идемпотентный DDL при старте.
2. **Доступ к данным:** тонкий слой `repo/*` с обычным SQL. Никакого ORM на M1.
3. **Деньги:** целые minor units (`INTEGER`), двойная запись через таблицу `postings`.
4. **Zen Money:** официальный API `https://api.zenmoney.ru/v8/diff/`,
   токен с `zerro.app/token`, инкрементальная синхронизация по `serverTimestamp`.
5. **Веб:** серверный HTML из Fastify, без сборки фронтенда. Next.js — когда появится
   сложный UI (бюджеты, графики, guard-панель).

## Почему не Prisma/Postgres сейчас

- Prisma добавляет генерацию, движки и вес к образу; для одного файла БД это оверхед.
- Postgres требует второго контейнера и усложняет бэкап для нетехнической семьи.
- Сырой SQL прозрачен и тестируется без магии.

## Когда пересмотрим

- Больше 50–100 тысяч операций или несколько семей на инстанс → Postgres.
- Нужны сложные отчёты и полнотекстовый поиск → FTS5 (SQLite) или Postgres.
- Появится мобильный клиент с конфликтующими офлайн-правками → серверный журнал изменений.

## Последствия

- Бэкап — копия `familyos.db` (плюс `-wal`/`-shm` при горячем копировании).
- Один процесс пишет в БД; горизонтальное масштабирование не поддерживается (и не нужно).
- Токены банков и Zen Money шифруются AES-256-GCM ключом из `FAMILYOS_SECRET`.
